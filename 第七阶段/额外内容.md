# 不使用Vuex时跨页面/组件共享状态、框架的利弊
> Vue2 时代 Vuex，Vue3 一般用 Pinia，题目说不用 Vuex，就是不使用专用状态管理库。

## 一、不用Vuex，如何跨页面共享状态
> 区分两个概念：**同应用内路由跳转（SPA，`router.push`）**、**真正新开页面（`window.open` / a标签target="_blank"，不同浏览器tab）**

### 1. SPA内部（同一个Vue实例，路由切换，没有销毁整个应用）
1. **全局对象 / 全局变量**
新建一个普通js文件，导出一个响应式对象。
```js
// store.js
import { reactive } from 'vue'
export const globalState = reactive({
  username: '',
  token: ''
})
```
各个页面直接 import 引入使用。
✅简单；❌页面刷新，数据全部丢失；**组件销毁不会自动清理，容易状态残留混乱**。

2. **provide / inject**
根组件App.vue provide出去，后代组件inject获取。
✅适合深层组件透传，不用层层props；
❌**跨路由页面共享能力弱**；修改来源不清晰，调试麻烦；不支持新开标签页。

3. **路由传参 `$route` / query / params**
- params：放在url路径；query放在url查询字符串。
适合**少量简单数据**，比如id、名称。
❌不能传复杂对象、函数；数据暴露在URL；刷新还在，但是大数据不适合。

### 2. 需要刷新页面 / 新开浏览器标签页（多tab之间）
内存里的JS对象全部失效，必须存浏览器存储：
1. `localStorage` / `sessionStorage`
- localStorage：永久本地存储，多tab共享；存字符串，对象要JSON序列化。
- sessionStorage：仅当前tab，关闭标签就清空。
> 缺点：只能存字符串；修改存储不会自动触发Vue响应式；需要自己封装监听。

2. `IndexedDB`：适合大量复杂数据，API繁琐。

3. `BroadcastChannel` API
不同tab之间通信，A标签页修改状态，通知其他标签页同步更新内存状态。

### 3. 事件总线（EventBus）Vue2常用，Vue3不推荐
`mitt`库，发布订阅模式。页面A派发事件，页面B监听事件接收数据。
✅跨组件传值；
❌**非常容易出现状态混乱**：忘记销毁监听，多次重复订阅，事件满天飞，不知道是谁触发。

## 二、什么场景会遇到“状态乱了”？
不用状态库的时候高频踩坑场景：
1. **组件复用、路由缓存keep‑alive**
页面被缓存没有销毁，旧的全局变量残留，再次打开页面还是上次旧数据。
> 例：表单页面，退出没清空globalState，下次进来直接拿到上一次用户填写的表单。

2. **EventBus事件监听没有off销毁**
组件多次挂载，重复注册监听，触发一次事件，回调执行N次，数据被多次覆盖。

3. **localStorage和内存状态不同步**
改了内存的变量，忘记同步写localStorage；或者别的tab修改localStorage，当前页面内存变量没更新。
> 一个tab改登录状态，另一个tab还是旧的登录信息。

4. **异步请求竞态**
两个接口先后回来，晚返回的接口覆盖早返回的数据，页面状态错乱。

> 小结：原生方式最大痛点：**状态来源分散，修改逻辑散落各个页面，没有统一管控，调试溯源困难**。

# 第二部分：框架（Vue为例）解决了什么痛点？带来哪些新复杂度
## ✅框架解决的痛点
1. **告别手动DOM操作**
原生JS要获取dom、修改innerText、处理dom事件；Vue声明式渲染，只操作数据，DOM自动更新。不用关心DOM细节。

2. **响应式系统**
数据改变视图自动更新，不用自己写监听、手动刷新页面。

3. **组件化**
页面拆成小组件，复用代码，便于维护；原生写页面容易大段html/js耦合在一起。

4. **虚拟DOM diff算法**
高效更新DOM，不需要全量重绘整个页面。

5. **配套生态**
路由vue‑router、状态管理Pinia/Vuex，提供一套标准化方案，多人协作有统一范式。

6. **编译时能力（SFC单文件组件）**
html、js、css写在一个`.vue`文件，scoped样式隔离，解决css污染。

## ⚠️框架引入的新复杂度
1. **学习成本**
需要学习框架特有概念：响应式原理、v‑if/v‑for、生命周期、props、emit、computed、watch、ref/reactive、虚拟DOM、钩子函数。原生JS基础好也需要重新理解一套规则。

> 坑：比如Vue3直接修改普通对象不会响应，必须用reactive/ref；很多新手踩。

2. **黑盒问题，调试门槛变高**
底层是框架封装，出bug的时候，错误栈会夹杂框架源码，不容易定位是自己代码问题还是框架行为。

3. **版本迭代与生态适配成本**
Vue2 → Vue3，API大量变更，旧项目升级成本高；第三方库需要适配对应版本。

4. **抽象带来隐形开销**
虚拟DOM、响应式代理有性能开销；简单小页面，用框架属于“大炮打蚊子”，打包产物体积更大。

5. **容易出现“框架思维”，遗忘原生基础**
很多同学只会写Vue，不理解DOM、事件循环、浏览器底层原理，遇到框架边界问题无从下手。

6. **状态管理的心智负担**
虽然Pinia解决共享状态，但是又需要理解store、action、state；小项目过重。
