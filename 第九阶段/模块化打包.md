# Webpack / Rollup / Parcel / Snowpack 
> 梳理：
1. **Webpack**：全功能应用打包器；
2. **Rollup**：ESM优先，主打**类库/组件库打包**；
3. **Parcel**：主打**零配置**应用打包；
4. **Snowpack**：开创**开发环境无打包（unbundled）ESM**方案（项目现已停止活跃迭代，团队转向Astro）。

> 概念区分：
- Bundled（传统打包）：开发时把全部模块打包成bundle；文件改动，整体重新构建；Webpack、Rollup、Parcel都属于这类。
- Unbundled（无打包开发）：开发服务器直接把单个文件转成浏览器原生ESM，浏览器自己做模块加载；只有Snowpack、Vite开发环境是这套思路。

## 1.每个工具核心定位、优缺点、适用场景
### Webpack
**定位：通用全能应用打包工具**，把一切文件都视作模块，支持CommonJS / AMD / ESM，loader处理各类静态资源，插件能力极强。
✅优点
1. 生态极其完善，loader/plugin数量庞大；
2. 强大代码分割`splitChunks`、按需加载、PWA、复杂应用定制能力拉满；
3. 兼容老旧浏览器、复杂依赖场景；
4. Webpack5做了缓存提升构建速度。

❌缺点
1. **配置复杂，学习成本高**；
2. 大型项目开发模式构建慢，HMR随着项目增大性能衰减；
3. Tree‑Shaking需要`sideEffects`配合terser压缩，不如Rollup彻底，会注入webpack运行时代码(runtime)。

**适用场景**：大型SPA、企业复杂Web应用、需要深度定制构建流程；做**业务应用**，不适合做开源类库。

### Rollup
**定位：ESM优先的打包器，专门面向JS库、组件库**，Vue、React、Lodash等库都是Rollup打包产出。
✅优点
1. **Tree‑Shaking效果最好**，基于ESM静态分析，输出干净几乎无多余运行时代码；
2. 可同时输出多种格式：`esm/cjs/umd/iife`，满足npm库多版本分发；
3. 配置简单。

❌缺点
1. 对CSS、图片、字体等静态资源原生支持弱，高度依赖插件；
2. CommonJS兼容需要插件；
3. **不擅长大型业务应用**；代码分割能力弱于Webpack。

> 补充：**Vite生产环境底层就是Rollup**。

**适用场景**：开发npm工具库、UI组件库、SDK；**不适合直接做业务SPA**。

### Parcel
**定位：零配置打包工具**，口号“zero‑config”，不用写loader/plugin，自动识别项目文件（html入口），自动处理TS、sass、图片、postcss等资源。
✅优点
1. 几乎不用写配置，上手简单；
2. 自动代码分割、自动优化、内置HMR；
3. 自动处理polyfill、兼容旧浏览器。

❌缺点
1. 可定制能力弱；复杂构建流程很难扩展；
2. 大项目构建性能一般；
3. Parcel2之后项目进入维护模式，不再活跃迭代，官方建议迁移Vite。

**适用场景**：小型项目、快速原型、demo、简单网页；不适合大型企业级项目。

### Snowpack
**定位：无打包开发模式（Unbundled Development）**，开发环境利用浏览器原生ESM，**不把全部代码打包成bundle**；修改文件只重新构建单个文件，冷启动飞快。
> 历史：Snowpack是Vite开发模式的灵感来源；项目停止开发，团队转向Astro框架（Astro底层基于Vite）。

✅优点
1. 开发服务器冷启动极快，项目规模变大，开发速度不会明显恶化；
2. 零/少配置；原生ESM；HMR；
3. 开发阶段没有整体打包开销。

❌缺点
1. **生产环境本身不做完整打包**，生产构建要外接Rollup/Webpack/Parcel插件，体验割裂；
2. 插件生态有限；项目不再维护；
3. 依赖需要预处理（esinstall）处理CommonJS第三方库。

**适用场景**：当年现代轻量web应用原型；现在新项目基本不选，迁移Vite。

## 2.对比总表
|对比维度|Webpack|Rollup|Parcel|Snowpack|
|---|---|---|---|---|
|核心定位|全能业务应用打包器|ESM库打包器|零配置应用打包器|基于ESM无打包开发工具|
|开发模式原理|全部模块打包bundle|打包bundle|打包bundle|**Unbundled 浏览器原生ESM**|
|Tree‑Shaking|需要sideEffects+压缩，一般|**效果最优**|中等|开发环境不做tree‑shaking，交给生产打包工具|
|静态资源(css/img)|✅loader完善|❌靠插件|✅开箱即用|✅插件支持|
|模块化规范|CJS/AMD/ESM全支持|优先ESM，CJS靠插件|全部支持|优先ESM，CJS需要esinstall转换|
|配置复杂度|高|中等|极低（零配置）|低|
|插件生态|极其丰富|库开发生态完善|中等|有限，项目停止迭代|
|生产构建产物|带webpack runtime|干净，runtime极少|自动优化|本身不打包，委托外部工具|
|典型适用|大型SPA业务项目|组件库、JS SDK、npm库|小项目、原型demo|历史项目；新项目选Vite替代|

## 3.重点问题
### Q1：Webpack vs Rollup，什么时候选谁？
> **业务应用选Webpack；写库/组件库选Rollup。**
- Webpack输出会有一套webpack runtime模块运行时代码，适合浏览器业务应用；
- Rollup输出干净，没有多余runtime，tree‑shaking强；用户导入你的库时，可以被上层项目继续tree‑shaking删减代码。
> 很多项目两者混用：业务代码Webpack，内部组件库Rollup打包。

### Q2：Snowpack和Vite的关系？
1. Snowpack最早提出unbundled开发，Vite开发模式思想借鉴Snowpack v1的esinstall依赖预打包思路。
2. Snowpack生产构建是外接第三方打包工具，割裂；**Vite开发esbuild预构建依赖，生产直接深度集成Rollup，一套插件同时工作在dev/build**，体验统一。
3. Snowpack已经停止迭代，团队转做Astro，Astro底层基于Vite。

### Q3：Parcel零配置原理是什么？
读取项目文件，自动识别文件后缀，自动下载对应的编译工具（sass、typescript），自动完成编译、资源处理、代码分割，**不需要开发者手动写loader/plugin配置**；代价是自定义能力受限。

### Q4：Unbundled（Snowpack/Vite开发环境）和传统bundled（Webpack）本质区别
- **Webpack**：dev模式把所有模块打包成少数bundle文件给浏览器；文件改动，重新执行打包逻辑。项目越大，重构建越慢。
- **Snowpack/Vite(dev)**：浏览器直接请求一个个单独ESM模块；第三方依赖提前预处理；源码文件按需实时转换；改哪个文件，只处理那一个文件，不需要整体重打包。
