## 1. 包管理工具最核心解决的问题是什么？不用包管理能不能做项目？

### 核心解决问题

1. **依赖获取与分发**：不用手动去各个官网下载第三方库源码，工具自动下载项目需要的代码包。
2. **依赖管理（传递依赖）**：A库依赖B，B又依赖C，传递依赖链条自动解析，不需要人工手动拷贝全部依赖。
3. **版本管控**：记录依赖版本，保证不同机器、不同开发者环境安装**完全一致的依赖版本**，解决“本地能跑，线上/别人电脑跑不起来”。
4. **依赖安装卸载**：一键增删依赖，自动维护依赖关系，不用手动复制删除文件。
5. **脚本执行**：封装项目命令（dev/build/test），统一项目执行入口。

> 
> 一句话总结核心：**管理第三方依赖的获取、版本、传递关系，保证环境可复现**。

### 不用包管理能不能做项目？

**技术上可以，但工程上完全不推荐**

- 原生方式：手动下载js库放到项目`lib`文件夹，通过`<script>`标签导入；前端可以直接CDN；后端手动下载源码。
- 缺点：
  1. 传递依赖噩梦：A包依赖10个包，每个包又有自己依赖，全部人工找齐；
  2. 版本无法锁定，升级库全靠手动替换文件；
  3. 没有版本约束，极易版本冲突；
  4. 共享项目时，需要把所有第三方库一起提交git，仓库体积爆炸；
  5. 没有构建脚本、没有生态能力。

小型demo、简单页面可以不用包管理；**现代中大型项目几乎不可能脱离包管理器维护**。

## 2. 依赖版本冲突一般怎么产生？你遇到过类似情况吗？

### 冲突产生的根本原因

> 
> npm/yarn 允许**同一个项目中，同一包存在多个不同版本**。冲突来源于：**不同依赖对同一个子包要求了互相不兼容的版本范围**。

举个场景：

```
项目
├─ 组件库A@2.0.0 要求：lodash@^4.17.0
└─ 工具库B@1.0.0 要求：lodash@^3.9.0
```

- `^4.17.0`：允许4.x版本；`^3.9.0`允许3.x；版本范围没有交集。
- 无法共用同一个lodash，node_modules里会同时存在 lodash@4 和 lodash@3。

#### 常见场景

1. **直接依赖和间接依赖版本要求不一致**：自己装的包V2，但是某个第三方库内部强制需要V1，版本范围不重叠。
2. **版本范围符号带来问题**：`^`、`~`模糊版本，不同时间安装拉取到不同版本，也会带来隐性冲突。
3. **包的破坏性更新（breaking change）**：同一个包大版本API完全变了，老库只兼容v1，新代码写的是v2。
4. **peerDependencies冲突（高频）**
`peerDependencies`对等依赖：插件期望宿主项目提供某个版本。
例：react插件要求 `react@>=18`，但是你的项目react@17，就会报peer冲突。插件不会自己安装react，要求宿主提供，版本不匹配直接告警/报错。

> 
> 区分：
> 
> 
> - 普通依赖冲突：可以安装多个版本共存，不一定报错，但是磁盘膨胀，甚至运行时异常；
> - peerDependencies冲突：不会自动安装，直接抛出警告，很容易运行报错。

### 实际开发遇到的真实案例

1. React项目，一个老图表库只支持`react@17`，项目升级react18之后，出现peerDependency报错；
2. webpack插件生态，部分插件只适配webpack4，项目升级webpack5后版本冲突；
3. lodash不同子依赖要求4.16和4.17，项目里同时存在两份lodash，打包产物体积变大。

### 常见解决手段

1. `resolutions(pnpm/yarn)` / `overrides(npm)`：强制统一子依赖版本；
2. 升级/降级上层依赖包，找到互相兼容的版本；
3. 升级废弃老旧第三方库；
4. 处理peer依赖：升级宿主版本。

## 3. pnpm 和 npm 的 node_modules 结构差异，为什么会影响安装速度与磁盘占用？

### npm（v2/v3）node_modules结构

npm v3之后采用**扁平结构(hoisting，提升)**

1. 尽可能把依赖提升到根目录`node_modules`；版本冲突的时候，才在子包目录嵌套安装对应版本。
2. 所有文件都是**完整复制**，每一个项目的node_modules都是一份独立文件拷贝。

问题：

1. 磁盘浪费：电脑多个项目使用同一个版本`lodash`，每个项目都复制一份完整文件；磁盘大量重复拷贝。
2. hoisting提升带来幽灵依赖：代码中引入没有在package.json声明的包，但是刚好被提升到根目录，可以运行；换环境安装，hoisting结果变化，直接报错。

### pnpm node_modules 结构

pnpm 引入**内容可寻址存储（content‑addressable store）全局存储仓库**

1. 磁盘上有一个全局store，文件**只存一份，按文件内容hash命名**；多个项目共用，相同版本文件不会重复存储。
2. 项目本地`node_modules`里面不放真实文件，大量使用**硬链接+符号链接**指向全局store。
3. 目录结构不会做无限制hoisting，结构更严格，规避幽灵依赖。

> 
> 硬链接：同一个磁盘文件，多个入口，不额外占用磁盘；符号链接：软链接，相当于快捷方式。

### 为什么速度更快、磁盘占用更低？

#### 磁盘占用优势

1. **全局单实例存储**：多个项目使用同一个版本的包，磁盘只保存一次真实文件；npm每个项目完整复制一份，重复冗余。
2. 只有修改过的文件才会新增存储，相同内容直接复用硬链接。

#### 安装速度优势

1. **不需要重复拷贝文件**：如果包已经存在全局store，不需要网络下载、不需要复制，直接建立硬链接，毫秒级完成安装；npm每次都要复制文件到本地node_modules，IO开销大。
2. 网络层面：同样会解析依赖，但是本地缓存复用效率远高于npm缓存。

#### 补充两者其他差异

1. npm的hoisting容易出现幽灵依赖；pnpm严格的目录结构，不允许导入未声明依赖；
2. npm扁平化逻辑复杂，冲突时嵌套；pnpm依赖结构清晰；
3. pnpm也支持 `hoist-pattern` 做部分提升兼容老旧包。

### 简单对比表

| 特性 | npm(node_modules) | pnpm(node_modules) |
| --- | --- | --- |
| 真实文件存储 | 每个项目完整复制 | 真实文件存在全局store，本地硬链接 |
| 多项目相同包 | 重复占用磁盘 | 全局复用，磁盘只存一份 |
| 文件IO | 大量复制文件 | 仅创建链接，IO极少，安装更快 |
| hoist扁平化 | 尽可能全部提升到根目录 | 有限提升，规避幽灵依赖 |
| 冲突处理 | 子目录嵌套安装版本 | 通过链接指向不同版本全局文件 |

> 
> 注意：pnpm的速度优势分两种场景：
> 
> 
> - **已经下载过该包**：pnpm优势巨大，直接链接；
> - **全新包第一次下载**：都需要网络请求，速度差距会缩小，但磁盘存储依然更省。
