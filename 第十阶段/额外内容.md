## 一、前后端分离带来的好处 & 产生的新问题
> 对比：传统服务端渲染SSR（JSP / PHP模板，后端渲染HTML页面返回浏览器）；前后端分离：后端只输出JSON接口，前端负责页面渲染，通过HTTP请求拿数据。

### ✅好处
1. **职责解耦，分工明确**
后端聚焦业务逻辑、数据存储、权限、接口；前端专注UI交互、页面体验。前后端可以并行开发，不需要等后端页面模板，提升团队开发效率。

2. **多端复用接口能力**
一套后端接口，可以同时服务Web前端、小程序、App客户端；不用为每个端写一套页面渲染逻辑。

3. **用户体验更好**
前端SPA单页应用，页面无刷新跳转；局部更新页面，减少整页刷新，交互流畅。

4. **技术栈解耦**
前后端技术栈完全独立。后端可以Java/Go/Python；前端Vue/React，互不约束；可以单独迭代升级。

5. **部署独立**
前端静态资源部署CDN；后端服务单独部署；可以独立发布版本。

### ❌带来新问题
1. **接口成为沟通核心，接口契约风险**
前后端依赖接口契约，字段、类型、格式一旦不一致，页面直接报错；接口文档更新不及时，是高频坑。

2. **产生跨域问题**
前端静态页面域名和后端接口域名/端口不一致，浏览器同源策略触发跨域，需要后端配置CORS或者代理。

3. **安全问题转移到前端**
- token、身份认证处理；CSRF、XSS风险；
- 前端存储敏感信息风险；权限校验不能只靠前端，后端必须二次校验；前端校验可以绕过。

4. **额外处理网络异常**
前端要处理http错误、超时、断网、加载状态、错误提示；传统服务端渲染由后端返回完整页面。

5. **SEO问题**
纯SPA客户端渲染，浏览器拿到空HTML，爬虫获取不到页面内容，不利于搜索引擎优化，需要SSR/SSG补救。

6. **开发联调成本增加**
联调阶段需要mock、代理；版本迭代接口变更，版本兼容需要处理；需要处理接口版本、新旧接口兼容。

7. **性能问题**
页面初始化需要请求多个接口，存在接口瀑布流；白屏问题，需要做loading、骨架屏。

## 二、调试前后端交互，先看前端还是后端？依据是什么
> 标准答案：**先定位问题来源，不是固定先看某一端，按顺序排查**
### 排查步骤
1. **第一步打开浏览器Network面板，看真实请求：请求URL、请求参数、Request Payload、HTTP状态码、Response响应数据**
- 看**请求本身对不对**：请求地址、请求方法GET/POST、请求头、传参是否和接口文档一致。

#### 情况1：请求就发错了 → 前端问题
请求地址错误、method不对、参数缺失/参数格式错误（比如传字符串后端要数字）、header没有携带token。👉**问题在前端**。

#### 情况2：请求成功发出，状态码200，但是返回数据不对
拿到后端返回response，对比预期数据：
- 如果返回字段缺失、字段类型错误、业务逻辑结果不对，但是前端请求参数完全正确 → **后端问题**。

#### 情况3：状态码 4xx
- 400 参数错误：看参数，参数构造错误前端；参数传对后端校验报错 →后端。
- 401/403鉴权：token没带、token过期前端；token合法后端拒绝访问 →后端。
- 404接口不存在：url写错前端；接口没部署后端。

#### 情况4：状态码5xx服务端错误
服务异常、报错堆栈，大概率后端；确认参数无误，后端服务内部异常。

#### 情况5：跨域报错
浏览器控制台出现CORS报错；请求甚至都没有到达后端服务，是后端没有配置跨域CORS。👉后端问题。

> 总结判断依据：
1. **看Network原始请求与响应，这是客观事实，不看代码主观猜测**
2. **请求是否符合接口契约：请求头、地址、方法、参数是谁产生的，谁负责；返回结果不符合契约，后端负责。**

> 工作小习惯：
不要直接甩给后端“接口报错”，直接复制network里的请求、参数、response，方便定位。

## 三、接口变更，前端如何稳妥适配？工程化方案
### 1. 朴素做法（不够工程化，手工）
1. 看文档变更，手动修改字段名；做兼容判断，旧字段存在就用旧字段，没有就用新字段；
```js
//兼容新旧字段
const name = res.newName ?? res.oldName
```
缺点：靠人，容易漏，文档和接口不一致，没有校验，上线容易出bug。

### 2. 更工程化的整套解决方案
#### ① 契约优先：接口文档 + OpenAPI(Swagger)，自动生成TS类型
后端维护OpenAPI(Swagger)接口契约文件。
前端用工具根据OpenAPI yaml/json**自动生成TS类型定义、请求函数**。
>工具：openapi‑typescript、orval。
- 后端接口字段修改 → 更新OpenAPI；前端重新执行脚本生成类型；
- TS直接编译报错：字段改名、删除，TS编译阶段就提示，**编译期发现问题，而不是线上运行时才报错**。
> 核心价值：把接口契约落实到类型层面，接口变更，TS直接拦截。

#### ② Mock服务
开发阶段使用Mock，基于OpenAPI契约生成mock数据，前后端并行开发。

#### ③ 接口版本管理（后端配合）
后端接口带上版本号 `/api/v1/user` `/api/v2/user`
- 迭代保留旧版本接口一段时间，前端逐步迁移，不要一次性全量切。
- 旧版本标记废弃`deprecated`，逐步下线。

#### ④ 请求层统一封装（axios二次封装）
统一拦截响应，做字段兼容、降级兜底。
```ts
//响应拦截器统一处理
instance.interceptors.response.use(res=>{
  //对废弃字段做兼容映射
  if(res.data.oldField && !res.data.newField){
    res.data.newField = res.data.oldField
  }
  return res.data
})
```

#### ⑤ 接口契约测试
- 自动化测试：基于契约做契约测试（Pact），保证接口契约不被破坏。
- E2E测试，覆盖接口变更后的页面流程。

#### ⑥ 废弃字段处理策略
后端标记字段deprecated，返回额外响应头提示废弃字段；前端拦截器捕获警告，控制台输出警告日志，提醒开发人员逐步移除旧字段逻辑。

#### ⑦ 联调 & 回归校验
接口变更后，不仅改代码，还要回归所有使用该接口的页面；避免只改一处，其他页面漏改。

### 工程化完整流程总结
1. 后端更新OpenAPI契约文件；标记废弃字段；必要时新增接口版本；
2. 前端拉取最新契约，脚本自动生成TS类型与请求函数；
3. **TS静态检查直接发现字段删除、重命名带来的代码问题**；
4. 必要时在请求层做临时兼容兜底逻辑；
5. 单元测试/契约测试验证；
6. 逐步移除旧字段兼容代码，完成迁移。

> ❗ 重点：**不要完全依赖手动看文档改代码，文档可能滞后；把接口契约变成TS类型，利用Typescript编译期检查，提前发现问题，这是最核心工程化手段。**
